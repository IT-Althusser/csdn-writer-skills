# Few-shot Examples

## 示例 1：知识点博客，先给架构

用户输入：

“写一篇 Spring 事务失效场景的 CSDN 博客，讲清楚为什么失效，给最小代码。”

理想处理：

- 先判定为知识点博客
- 先给文章架构
- 围绕“失效原因 + 最小复现 + 排查方法”展开
- 不强行扩成完整项目实战

理想首轮输出示例：

```md
标题建议：Spring 事务为什么会失效？5 个高频场景 + 最小复现代码

这篇文章可以按“现象 -> 原因 -> 复现 -> 排查”这条主线来写，不往项目实战扩。

一、先看现象：为什么方法加了 `@Transactional` 还是没有回滚
二、5 个最常见的事务失效场景
1. 同类方法内部调用
2. 方法不是 `public`
3. 异常被吃掉，没有继续抛出
4. 遇到的异常类型不会触发默认回滚
5. Bean 没有被 Spring 正确代理
三、用一个最小示例复现“同类调用导致事务失效”
四、排查事务失效时可以怎么定位
五、写业务代码时如何提前规避

如果你认可这条主线，我再继续展开正文和最小代码。
```

不要这样处理：

- 上来直接写完整长文
- 把主题拉成“订单项目事务实战”
- 只讲定义，不给复现和排查入口

## 示例 2：根据 dayXX 笔记写文章，不能越界

用户输入：

“根据我的 day03 笔记写一篇文章，不要超出笔记框架。”

理想处理：

- 先读 day03 笔记
- 先给架构
- 正文只补笔记中已有知识点对应的少量代码证据
- 不擅自补完整 CRUD

理想首轮输出示例：

```md
我先按你这份 day03 笔记来定文章主线，不额外扩写到笔记外的员工 CRUD。

标题建议：苍穹外卖 day03 学习笔记｜菜品管理这一节到底学了什么

文章架构建议：

一、这一节的目标：菜品管理要解决什么问题
二、从前端请求到后端接口，当前笔记覆盖了哪些能力
三、和菜品新增直接相关的字段、参数和校验点
四、这节代码里最值得理解的调用链
五、学完这一节后，自己应该能完成哪些最小验证

这版架构会严格卡在你笔记已经出现的知识点里，不会额外补分页、启禁用、删除、编辑这些没要求展开的内容。
如果你认可，我再按这个结构写正文。
```

不要这样处理：

- 一看到“day03”就默认补全整个模块
- 为了显得完整，把新增、分页、删除、启禁用全写进去
- 还没看笔记就先按项目代码自作主线

## 示例 3：低分文章重写，不是改句子

用户输入：

“这篇只有 77 分，帮我重写到能发，问题是太散了。”

理想处理：

- 先判断为低分重写
- 不只改措辞
- 重新提炼主线
- 增加验证入口、失败排查、适用边界和可迁移方法

理想首轮输出示例：

```md
这篇文章如果只修句子，分数还是上不去。它现在的主要问题不是表达，而是主线散，像知识点罗列。

我建议把它改成“登录认证链路”这条主线来重写，结构可以这样定：

一、先回答问题：用户登录后，系统到底怎么识别当前身份
二、登录请求进入后端后，认证链路是怎么走的
三、JWT 在这条链路里负责什么，拦截器又负责什么
四、这条链路最容易出错的 3 个位置
五、自己排查登录失效时应该先看哪几个点
六、这套做法迁移到别的后台项目时要改什么

如果你同意，我就按“链路重建”的方式整篇重写，而不是停留在润色层面。
```

不要这样处理：

- 直接开始替换同义词
- 只加几个过渡句，就说完成重写
- 保留原来散乱的小标题顺序不动

## 示例 4：功能文，标题直接对应功能

用户输入：

“根据菜品管理这块代码写一篇 CSDN 文章，先给我架构。”

理想处理：

- 先判定为项目功能文
- 标题直接对应功能，不加花哨包装词
- 用接口、参数、调用链支撑主线

理想首轮输出示例：

```md
标题建议：苍穹外卖 day03｜新增菜品功能实现

这篇文章适合按“一个新增功能从页面到数据库怎么落地”来写，结构先定成下面这样：

一、先看需求：新增菜品到底要提交哪些信息
二、前端提交的数据格式和后端接口如何对上
三、Controller、Service、Mapper 各自负责什么
四、菜品基本信息和口味数据为什么要分开处理
五、自己联调这个功能时该怎么验证
六、这一套新增流程还能迁移到哪些类似功能

如果你认可，我再继续把每一节展开成正文。
```

不要这样处理：

- 标题写成“从前端到后端的完整闭环探索”
- 一上来就铺垫很多空话
- 只贴代码，不解释参数、返回值和调用链

## 示例 5：用户让直接改 skill，不进入博客流程

用户输入：

“改一下这个 skill，把默认流程换成先出架构。”

理想处理：

- 识别为修改 skill 本身
- 直接编辑当前 `SKILL.md`
- 不进入博客写作流程

理想响应方向：

- 说明将修改 skill 文件
- 直接更新规则
- 汇报改动结果

不要这样处理：

- 给一篇博客架构
- 进入文章写作模式
- 只口头建议，不真正修改文件
