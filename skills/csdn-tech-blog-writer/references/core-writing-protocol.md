# CSDN 博客核心写作协议

本文件合并原来的执行协议、课程项目笔记风格、表达风格、质量评分和短验收。以后写 CSDN 博客优先按这里执行，不再打开一堆重复模板。

## 1. 先判断当前任务

先把用户请求分到一个明确动作：

- **先出架构**：只给标题和目录结构，不写完整正文。
- **知识点博客**：围绕一个注解、API、机制、配置、错误、工具或最佳实践写清楚，不要求完整项目三层代码。
- **按笔记写正文**：用户笔记是主线，代码只是证据。
- **按功能代码写正文**：功能实现是主线，必须写 Controller -> Service -> Mapper/SQL 闭环。
- **低分重写**：用户给出 70、77、82 这类分数时，必须按评分问题重写，不做表面润色。
- **修改 skill**：直接修改 skill 文件，把本轮失败变成硬规则。

如果用户同时要多篇文章，逐篇隔离主题。第一篇的边界不能被第二篇污染。

### 文章类型判定表

| 用户说法 | 判定类型 | 必须做 | 禁止做 |
| --- | --- | --- | --- |
| “写一篇 `ThreadLocal` / `PageHelper` / 某个注解知识点博客” | 知识点博客 | 写场景、概念、最小代码、执行流程、常见坑、验证方式 | 不强行凑 Controller -> Service -> Mapper |
| “根据 day02 笔记写博客”“不要超出我的笔记框架” | 课程笔记文 | 先读笔记，以笔记知识点为边界，用代码补证据 | 不把其他文章或完整功能实现混进来 |
| “写新增员工/菜品管理/某个功能代码” | 项目功能文 | 写功能目标、Controller、Service、Mapper/SQL、验证和失败点 | 不写成泛泛知识点清单 |
| “这篇只有 70/77/82 分，优化” | 低分重写 | 先列 3 条扣分原因，再重选主线和重写正文 | 不只改句子或加字数 |
| “润色/按我的风格改” | 润色/风格适配 | 先读原文，保留用户结构和删改意图 | 不恢复用户删掉的啰嗦段落 |

## 2. 默认先架构后全文

新写文章默认两步走：

```text
第一步：输出文章架构，说明标题、主线、每节写什么、哪些代码/文档作为证据。
第二步：用户赞同、确认、说“继续”或提出修改后，再生成完整正文。
```

只有在用户明确说“直接写全文”“不用先问”“直接生成文章”时，才可以跳过架构确认。

输出架构时不要写长正文，只写：

- 推荐标题；
- 文章类型；
- 主线；
- 目录结构；
- 每节使用的证据；
- 明确不写什么，防止跑题。

标题约束：

- 标题必须贴主题本身，不能自作聪明包装。
- 用户让写功能，就直接写功能标题，例如“苍穹外卖 day03 | 菜品管理”“新增菜品功能实现”。
- 不要随意加“从……到……”“完整闭环”“这些东西”“一篇带你搞懂”之类显 AI 的包装词。

### 本地文件输出位置

如果需要把文章保存成 Markdown 文件，默认输出到 `D:\codex-content\<yyyy-MM-dd>`，日期按当前日期计算。除非用户明确指定其他路径，不要默认保存到 Codex 工作区 `outputs` 目录。

## 3. 知识点博客路线

当用户只要求写某个知识点，例如 `@PathVariable`、`ThreadLocal`、`PageHelper`、JWT、AOP、Redis 缓存、MyBatis 动态 SQL、Spring MVC 日期格式、yml 配置、某个报错或某个工具用法时，按知识点文写，不要强行写成完整项目实战。

知识点文优先结构：

```text
标题：准确点名知识点和场景
前言：1 段、2-3 句话完成引入，先概括核心内容，再说明内容之间的主线；说明读者要解决的问题，不写背景铺垫、作者感受或“本文将……”
一、使用场景：这个知识点在什么业务/开发场景下出现
二、核心概念：用自己的话讲明白，不写百科腔
三、最小代码：只放理解这个点必要的代码
四、执行流程：请求/数据/线程/SQL/配置如何流动
五、常见坑和排查：按主题需要写 1-3 个容易错的点
六、项目中怎么验证：有真实结果写真实结果，没有就写可验证路径
七、总结：简短收束关键结论；有对应内容时补一个可迁移判断方法或易错点
```

写知识点文时要注意：

- 不要为了“项目感”硬凑 Controller -> Service -> Mapper；只有知识点本身涉及三层链路时才展开。
- 最小代码比大段源码更重要。只贴和知识点直接相关的注解、方法、配置、SQL 或错误片段。
- 如果是框架/API/CLI/云服务相关知识点，必须按工作区规则用 `ctx7` 查当前文档。
- 如果用户给了项目代码，就用当前项目做例子；如果没有项目代码，可以写通用最小示例，并标注为示例。
- 标题不要夸张，不写“一文吃透”“保姆级”。
- 不要写“你在笔记里提到”“我这里准备讲”“这篇文章我打算”这类写作者自述句，正文默认面向读者讲解。

知识点文常见主线示例：

- `@PathVariable`：URL 模板变量 -> 参数绑定 -> 类型转换 -> 调接口时路径和 query 的区别。
- `ThreadLocal`：一次请求线程内保存当前用户 -> 拦截器写入 -> 后续业务读取 -> 请求结束清理。
- `PageHelper`：调用顺序 -> 拦截紧跟查询 -> 封装 total/records -> 版本兼容检查。
- yml 配置：环境激活 -> 占位符取值 -> dev 配置提供真实值 -> 密钥脱敏和缩进坑。
- Spring MVC 日期格式：旧写法不适配 -> 当前依赖 -> 消息转换器/格式化器 -> 验证返回格式。

## 4. 课程项目笔记文的硬边界

用户提供 dayXX 笔记时，先读笔记并锁定主题边界。

必须遵守：

- 笔记没有涉及完整功能实现，就不要强行补全完整 CRUD。
- 笔记提到“用我的代码说明”，只补该知识点对应的最小代码证据。
- 笔记文可以写接口自测、DTO/Entity/VO、配置、异常、分页、认证、日期格式等通用机制，但不要平均铺开成清单。
- 如果笔记内容散，先选一条主线，例如 **后台接口自测闭环**、**登录认证链路**、**版本适配排查链路**。
- 默认先输出架构并等待用户赞同，不要直接写完整文章。

### 纯文字笔记加参考文：博客化规则

当用户提供纯文字课程笔记、课堂截图和一篇或多篇参考文章，并要求写成博客、补充内容或借鉴展开方式时，必须读取 [course-note-blogging.md](course-note-blogging.md)。

这类文章的边界与表达同时受控：

- 用户笔记及其截图是章节范围和首要事实来源；参考文章只能补充与现有章节直接对应、已核验的内容。
- 参考文与当前章节不一致时，只能借鉴组织方式、段落展开和解释粒度，不能把其知识点迁入正文。
- 正文必须是面向读者的博客，不得出现“笔记中”“课堂图”“根据提供的材料”“我看到的图片”等来源痕迹；来源只放在文末参考资料。
- 不能逐条改写原始笔记。每个重点概念至少补足“作用、机制、区别、流程、字段或例子”中的一项，且只扩展少数关键点，不平均灌水。

本轮失败教训：

- Day02 第一篇基于笔记知识点，不应写成“新增员工、分页查询、启用禁用、编辑员工”的员工功能实战。
- 员工功能实现可以作为第二篇单独写，不能混进第一篇。
- 前言要短，承担引入作用：用 2-3 句话概括文章覆盖的核心内容，并说明这些内容如何串成一条主线。知识点或课程笔记文章可采用“这篇整理……，包括……；这些内容串起来可以完成……”的句式；功能文章直接写功能目标和代码需求。
- 前言不要把标题和目录逐项再抄一遍；只保留主题范围、读者问题和阅读路线，通常不超过 120 字，内容较短时可以更短。
- 不能把文章写成“表面上看……其实……”“真正串起来之后会发现……”这种先绕后说的 AI 套路。
- 不能频繁写“项目里的做法很清楚，一共分三步”“这个地方值得单独讲清楚”“这里最值得记住的是”这类空过渡。

## 5. 项目功能文的闭环

只有当用户明确要求写某个功能实现时，才按功能文写。

每个功能优先形成：

```text
功能目标
-> Controller 入参和接口路径
-> Service 业务处理和字段补充
-> Mapper / XML / SQL 落库或查询
-> 验证方式和常见失败点
-> 涉及知识点
```

不要把项目文写成文件清单；也不要只贴代码不解释参数、返回值、配置项和 SQL 条件。

## 6. 低分重写规则

70-79 分常见问题：

- 开头像日记，没有说明读者能解决什么问题。
- 正文像知识点清单，缺少项目证据和自测闭环。
- 代码贴了，但没有解释参数、返回值、配置、访问路径。
- 工具类内容只说“是什么”，没有写“怎么验证，失败先查哪里”。
- 结尾只是复述目录，没有沉淀可迁移方法。

80-89 分常见问题：

- 主线不够聚焦，多个主题平均展开。
- 真实现象、验证入口、失败排查不够。
- 版本敏感内容没有写清当前依赖和官方依据。
- 结尾只有总结，没有明确方法或易错点；有对应内容时补一个可迁移的判断方法或易错点，没有就用 1-2 句收束关键结论。

低分重写必须这样改：

1. 先写 3 条扣分原因，说明为什么不值得推荐。
2. 重选一个主线，不继续堆字数。
3. 每个核心小节补一个作用：解释背景、承接代码、分析卡点、给出验证方式或说明边界。
4. 对 Apifox、yml、PageHelper、日期格式这类实操点，写清预期现象和失败排查顺序。
5. 对版本敏感内容，用当前项目依赖和 `ctx7`/官方文档支撑。
6. 结尾沉淀一句可迁移方法，而不是复述目录。

## 7. 证据和 ctx7

正式文章中的真实技术细节必须来自：

- 用户笔记、草稿或历史文章；
- 当前项目源码、配置、SQL、依赖；
- `ctx7` 获取到的当前官方文档。

纯文字笔记文额外遵循以下优先级：用户正文与截图 -> 已核验且主题匹配的参考文章 -> 当前官方文档。若参考文章仅用于写法借鉴，不得将其当作正文事实来源或以其内容填充无关章节。

必须有来源的内容：

- 接口路径、请求方式、参数、响应结构；
- SQL、Mapper XML、实体字段、配置项；
- 依赖版本、启动命令、测试命令；
- 运行结果、截图、日志、性能数据。

如果没有真实运行结果，只能写“可以这样验证”或“按当前代码推断”，不能写成已经验证成功。

涉及 Spring Boot、Spring MVC、MyBatis、PageHelper、Lombok、OpenAPI、Apifox、OSS、Redis、微信等库/框架/API/云服务时，按工作区 `AGENTS.md` 使用 `ctx7`。如果额度或网络失败，直接说明无法确认最新状态。

## 8. yml、密码和配置写法

写 `application.yml` / `application-dev.yml` 时必须讲清：

```text
application.yml：公共结构、环境激活、占位符
application-dev.yml：开发环境具体值
```

必须覆盖：

- `spring.profiles.active` 如何激活环境；
- `${...}` 占位符如何从环境配置取值；
- yml 缩进、冒号后空格、同级对齐；
- 密码、Token、Secret、AccessKey、真实 IP、手机号、邮箱必须脱敏。

示例中的敏感值统一写成：

```yaml
password: ******
access-key-id: ******
access-key-secret: ******
```

不要把本地真实密钥、云服务 AK/SK、微信 secret、数据库密码原样写进博客。

## 9. 表达风格

目标是像认真整理项目笔记的人，不像模板化 AI。

写法要求：

- 前言短，直接点题并完成引入：先说清文章覆盖什么，再说清这些内容怎样连起来解决问题。
- 前言不要写空铺垫，不要写“所以这篇文章我不打算”“表面上看”“真正会发现”“其实先解决了一个更基础的问题”这类绕弯句。
- 多用自然陈述句，少用连续设问、反问、口号式总结。
- 段落短，每段只讲一个意思。
- 代码后紧跟解释，具体到变量、参数、返回值、配置项、SQL 条件或调用链。
- 写 MySQL/SQL 主题文章时，SQL 语句统一使用小写关键字；代码块和正文中的 SQL 片段都按 `create`、`select`、`from`、`where`、`with check option` 这类小写形式处理。
- 感悟要贴着卡点写一两句，不要扩成空泛心得。
- 不主动追加“推荐标签”“后续计划”这类尾巴，除非用户要求。
- 文章首先要像博客：用自然段讲清场景、判断和过程，再用少量格式标记帮助扫描。不要把正文写成特殊符号堆叠、版本说明或材料摘录。
- 加粗优先用于关键结论、步骤名、字段解释和易错提醒；不要整段加粗，也不要为了装饰给普通技术名词加粗。
- 反引号只保留不可替代的精确标识。普通概念、常见英文词和一般技术名词直接写，不要为了“像技术文章”到处套反引号。
- 正文不要暴露写作过程，不要出现“你的笔记上写”“我看到你的代码里”“这篇文章下面我分三步讲”这类元叙述。
- 正文必须直接面向读者解释场景、机制、代码行为和风险。代码段前后不得用介绍材料或安排写作步骤的口吻，例如“下面是只使用 StringRedisTemplate 普通命令的实现”“项目里的实现与这里一致”“先补充几个 import”“把以下方法放进某个类”。应改为说明实际行为，例如“加锁时，setIfAbsent 在写入锁标识的同时设置过期时间。释放时先比较锁标识，再删除锁：”。凡是只告诉读者接下来会展示什么、材料来自哪里、代码应该如何拼装，却没有讲清技术行为的句子，都应改写。
- 纯文字笔记文还要删除“笔记中”“课堂图”“课程资料显示”“根据材料”等来源标签；用自然的概念说明、图题或段落承接替代。
- 版本信息只在确实影响行为、兼容性或排查时出现。不要使用“直接版本中”“本版本中新增”“当前版本中就是这样”这类生硬的版本宣告；改成结合项目依赖和现象的自然叙述，并说明读者该如何验证。
- 除非在纠正明确误区，否则少用“不是……而是……”“很多人以为……但实际上……”这类先抑后扬句式，一篇文章最多 1 次。
- 总结必须用一段简短文字收束，优先写成“这篇解决了什么问题，关键判断是什么”；有对应内容时再补 1 个可迁移方法或易错提醒，没有就用 1-2 句收束关键结论。不要复读目录、逐条重述正文、扩展后续计划或写大段空泛方法论。
- 全文保持信息密度，删除不增加事实、步骤、边界或验证价值的过渡句、感想句和重复解释；能合并的相邻段落合并，能一句说清的不要拆成多段。

## 10. 引用、加粗、反引号数量门禁

写完文章后必须做一次格式自检，检查三类标记：

```text
引用：Markdown 中以 > 开头的引用块
加粗：**...** 包住的片段
反引号：正文里的 `...` 内联代码片段，不统计代码块围栏
```

自检规则：

- 不强制引用、加粗、反引号三者都出现。没有就没有，不为了凑格式硬加。
- 引用通常控制在 0-2 个；加粗只保留真正帮助扫描的重点；正文内联反引号默认控制在 0-3 个，确实需要区分精确标识时最多 5 个。
- 任意一类超过合理数量，就删减到读者能自然阅读的程度；删减后仍然显得乱时，直接取消该类大多数格式，只保留 1-3 个最必要的。
- 普通中文解释不要套反引号；普通段落不要为了强调而频繁加粗。
- 引用优先用于用户笔记原话、官方文档结论或核心提醒；没有必要就不用。
- 正文默认采用“加粗优先、反引号从严”模式：
  - 非代码块场景下，反引号优先控制在 3 个以内；
  - 方法名、注解名、接口路径之外，能不用就不用；
  - 普通概念、普通英文词、常见类名优先直接写中文或用加粗。

## 11. 交付前实际检查

交付前必须自查：

- 文章主线是否只有一个；
- 是否选对文章类型：知识点文、笔记文、功能文不要混用；
- 是否严格回答用户当前这篇文章的边界；
- 是否把其他文章的功能代码混进来；
- 是否有项目代码或官方文档证据；
- 是否有验证入口或失败排查；
- 是否有版本/配置/敏感信息边界；
- 是否完成引用、加粗、反引号三类格式自检：引用通常不超过 2 个，正文内联反引号默认不超过 3 个，确需保留时最多 5 个，加粗只留下关键重点；
- 是否没有模板占位符、旧项目名、未脱敏密钥；
- 是否能直接复制到 CSDN。
- 纯文字笔记文是否已检查：正文没有来源标签；参考文没有越界注入无关章节；重点概念已经得到对应扩展；图片紧邻其对应知识点；文末来源与正文事实边界一致。

