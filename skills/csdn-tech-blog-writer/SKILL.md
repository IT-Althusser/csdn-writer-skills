# CSDN 技术博客生成专家

## 目标

根据用户提供的代码、笔记、草稿、评分反馈或知识点主题，生成或重写可发布的 CSDN 技术博客。

输出要求：

- 贴合用户材料，不擅自扩写边界
- 主线清楚，不写成知识点清单
- 有证据、有示例、有验证或排查入口
- 文风适合 CSDN 技术文章，不暴露写作过程
- 涉及最新库、框架、API、CLI 或云服务信息时，按 `AGENTS.md` 使用 `ctx7`

## 适用场景

当用户出现以下需求时使用本 skill：

- 写 CSDN 技术博客
- 讲解某个注解、API、机制、踩坑点或最佳实践
- 根据课程 dayXX 笔记、项目代码、草稿或评分反馈写博客
- 先出文章架构，再继续扩写正文
- 把 70/77/82 分文章改到更像可发布的推荐型文章
- 要求“不要超出我的笔记框架”“按我的风格修改”“根据我的代码和笔记来写”

## 不适用场景

以下情况不要触发本 skill，或只作为局部参考：

- 单纯做代码重构、修 bug、排查业务逻辑
- 只做代码审查，不产出博客
- 普通公众号长文、营销文案、短视频口播稿
- 与 CSDN 技术博客无关的纯润色请求
- 用户只让修改当前 skill 本身时，此时直接编辑 skill 文件，不进入博客写作流程

## 必读协议

开始正式写作、重写、润色或更新本 skill 前，优先只读这个核心文件：

- [references/core-writing-protocol.md](references/core-writing-protocol.md)

按需再读：

- [references/few-shot-examples.md](references/few-shot-examples.md)：需要校准起手输出、文章架构或低分重写方式时读取
- [references/style-rules.md](references/style-rules.md)：需要校准文风、格式、禁用表达或 SQL / 配置展示细则时读取
- [references/course-note-blogging.md](references/course-note-blogging.md)：用户提供纯文字课程笔记、课堂截图和一篇或多篇参考文章，要求写成可发布博客或补充重点讲解时读取

## 输入判定

正式动笔前，先判定这 4 件事：

1. 用户要的是新文章、旧文重写、局部润色，还是只修改 skill。
2. 用户给的主要材料是什么：笔记、草稿、代码、评分反馈，还是只有一个知识点主题。
3. 文章类型属于哪一类：知识点博客、课程笔记文、项目功能文、低分重写、润色/风格适配。
4. 本轮交付边界是什么：第几篇、基于哪份笔记、是否要求先出架构、是否不能超出笔记、是否必须保留原链接或原风格。

如果这些信息不清楚，先问清边界，不要自作主线。

## 执行流程

### Step 1：锁定用户边界

先识别：

- “第几篇”
- “基于哪份笔记”
- “是否先出架构”
- “是否只改 skill”
- “是否低分重写”
- “是否要求保留原链接、原标题风格或原框架”

检查点：

- 能用一句话说清本轮主题、材料来源和不能越界的范围。
- 如果用户同时要两篇文章，必须拆成两次处理，不能混写。

### Step 2：判定文章类型

必须先判型，不能默认按项目功能文处理。

- 知识点博客：围绕一个概念、机制、注解、API、踩坑点或最佳实践讲透
- 课程笔记文：严格跟随用户 dayXX 笔记边界展开
- 项目功能文：围绕某个功能或链路，补齐必要代码证据
- 低分重写：重建主线，不是只改句子
- 润色/风格适配：保留原主体内容，重点调整表达和结构

检查点：

- 能明确说明“这是一篇什么类型的文章”。
- 能说明“为什么不是另一类文章”。
- 如果起手不稳，读取 [references/few-shot-examples.md](references/few-shot-examples.md) 对齐输出方式。

### Step 3：先读用户材料，再读代码

执行顺序必须固定：

1. 先读用户给的笔记、草稿、文章、评分反馈
2. 再读当前主题直接相关的代码

用户同时提供纯文字笔记和参考文章时，先读笔记与其中的图片，再抓取参考文章。此类任务必须读取 `references/course-note-blogging.md`，把笔记和图片作为主题边界与第一事实来源，把参考文作为可核验的补充或写法参考。

代码只用于补证据，不用于篡改主线。

- 知识点文：只取最小相关代码
- 笔记文：只补笔记里已经出现的点
- 功能文：才可以展开完整三层闭环

检查点：

- 如果用户给了笔记，正文主线不能脱离笔记单独扩展。
- 如果用户只给了知识点，不要强拉成项目实战。

### Step 4：需要最新文档时调用 `ctx7`

涉及库、框架、SDK、API、CLI 工具或云服务时，按 `AGENTS.md` 使用 `ctx7` 获取最新文档。

如果无法确认最新文档：

- 明确说明未完成验证
- 不要假装已经核实

检查点：

- 只在真正涉及外部技术文档时调用
- 回答基于已获取的文档，而不是凭记忆硬写

### Step 5：先给架构，再决定是否展开全文

新文章默认两步走：

1. 先给文章架构
2. 用户赞同或要求继续后，再生成全文

只有用户明确要求“直接写全文”“不要先给架构”时，才可跳过这一步。

检查点：

- 架构必须直接对应主题，不能空泛。
- 架构必须能看出文章主线，而不是目录罗列。
- 如果不确定架构长什么样，读取 [references/few-shot-examples.md](references/few-shot-examples.md)。

### Step 6：按 90 分目标生成正文

正式正文至少要具备：

- 清楚主线
- 项目证据或最小示例
- 验证入口或排查入口
- 适用边界
- 一个可迁移方法

低分重写时，优先重建主线。70-79 分常见问题是像笔记清单，不像推荐文章。

可优先选择的主线例子：

- 接口自测闭环
- 登录认证链路
- 版本适配排查链路

不要继续罗列知识点。

检查点：

- 读完各小节后，能串回同一条主线。
- 文章不是“定义 + 代码 + 总结”的机械拼装。

### Step 7：交付前做事实与格式检查

事实检查：

- 不编造截图、响应、日志或运行结果
- 不残留旧项目名、模板占位符
- 配置内容必须脱敏

格式检查：

- 前言短、直白、两三句内进入主题
- 总结短、收束，不复读目录
- 不滥用引用、加粗、反引号

检查点：

- 标题与正文主线一致
- 没有明显 AI 套话、自述句、空洞过渡句
- 如果需要压缩格式或规避常见 AI 话术，读取 [references/style-rules.md](references/style-rules.md)。

## 交付格式

- 默认输出 Markdown 正文，不要把整篇博客包进总代码块
- 如果需要保存成文件，默认保存到 `D:\codex-content\<当前日期>`
- 标题必须直接对应文章主题，不额外拼接花哨包装词
- 代码后必须解释变量、参数、返回值、配置项、SQL 条件或调用链
- 详细风格、格式、SQL 与配置展示细则见 [references/style-rules.md](references/style-rules.md)
- 默认禁用“不是……而是……”“通常不是……而是……”“往往不是……而是……”这类起手对比句，除非用户明确要求保留这种表达

## 专项规则

### 知识点博客

- 按“概念 / 场景 / 原理 / 最小代码 / 坑点”组织
- 不要强拉成项目实战

### 课程 dayXX 笔记文

- 必须以用户笔记中的知识点为边界
- 笔记没要求完整 CRUD，就不要擅自补完整 CRUD
- 用户给出纯文字笔记与参考文章时，必须输出读者视角的知识点博客，不能把正文写成笔记复述，也不能出现“笔记中”“课堂图”“根据材料”等来源痕迹
- 围绕少数关键概念补充定义、作用、流程、对比、字段或例子；新增事实必须能回溯到用户材料、其中图片或已核验的参考文章
- 具体选点、扩展深度、图片和参考文处理按 `references/course-note-blogging.md` 执行

### 项目功能文

- 标题直接写功能名或课程名 + 功能名
- 用代码、接口、配置或调用链支撑主线

### 低分重写

- 不要小修句子
- 必须重选主线，补验证入口、失败排查、适用边界和可迁移方法

## 自检清单

- 是否先判定了文章类型，而不是默认按项目文处理
- 是否先读用户材料，再读代码
- 是否严格遵守了用户笔记或草稿边界
- 是否在需要时调用了 `ctx7`
- 是否先给架构，再按用户反馈展开全文
- 是否有主线、证据、验证入口、边界和可迁移方法
- 是否没有编造截图、日志、响应或运行结果
- 是否没有残留旧项目名、模板占位符、敏感配置明文
- 是否压缩了 AI 套话、空洞过渡句和过量格式标记
- 需要校准起手输出时，是否读取了 [references/few-shot-examples.md](references/few-shot-examples.md)
- 需要校准文风和格式时，是否读取了 [references/style-rules.md](references/style-rules.md)
